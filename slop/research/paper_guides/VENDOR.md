### Code-only partial clones and small HF archive (follow-up)

- Cloned both GitHub repositories using `git clone --filter=blob:limit=1m --no-checkout <url> docs/vendor/<name>`. The full-history science clone hit the shell's hard 60-second timeout while accumulating over 1 GB of small historical blobs; removed that incomplete clone and repeated with `--depth 1`. Constitutional adapters retains full history. Both final HEADs match the supplied pins.
- Before checkout, used GitHub's recursive tree API at each pinned commit to obtain paths and sizes without lazy-fetching missing blobs. Selected text/source extensions (`.py`, `.sh`, `.bash`, `.yaml`, `.yml`, `.toml`, `.md`, `.rst`, `.txt`, `.in`, `.cfg`, `.ini`, `.jinja`, `.j2`, `.sql`, `.tex`, `.js`, `.ts`, `.sbatch`, `.patch`, `.env`, `.service`, `.timer`), root files and `LICENSES/`, always excluding blobs ≥1 MiB. Excluded science's top-level `artifacts/`; excluded constitutional adapters' `corpora/`, `data/`, `objects/` and `tests/`. These are inspection checkouts, not complete runnable reproductions. JSON/JSONL payloads, notebooks and binary results are omitted.
- Applied the exact selected paths with `git sparse-checkout set --no-cone --stdin`, then `git checkout HEAD`. Registered both existing clones with `git submodule add <url> docs/vendor/<name>` and moved their Git directories into the parent with `git submodule absorbgitdirs`. No read-only `.git/config` error or fallback occurred. Sparse patterns and partial-clone settings are **local Git metadata**, not carried by the gitlink: a normal future `git submodule update --init` does not recreate these size limits and can fetch the large data. Reapply a filtered clone and sparse selection before checkout.
- Science: **2,625 files / 25,748,184 Git content bytes / 32,960,512 allocated working-tree bytes**; Git metadata/object store **477,736,960 bytes**. Constitutional adapters: **2,837 files / 82,493,543 Git content bytes / 89,702,400 allocated working-tree bytes**; Git metadata/object store **70,926,336 bytes**. Working-tree sizes exclude Git metadata and are each below **100,000,000 bytes**. The 1 MiB filter is per blob, not an aggregate object-store cap: it still downloads many smaller data/result blobs into Git, especially for science. They are not checked out.
- An initial `git ls-tree -r -l HEAD` inspection of constitutional adapters unexpectedly lazy-fetched large blobs to report sizes; it was stopped at the hard timeout. Removed that temporary clone and recloned before the final sparse checkout. Final stores contain **no blob ≥1 MiB**; the fetched temporary blobs were discarded. Tree API metadata avoids this trap.
- HF generation prompts: pinned revision `52279279350f88dc4e9d923d4d0ab9e50c125671`; recursive listing contains exactly four files totaling **55,759 bytes**, below the 50 MB limit, so fetched all four (`.gitattributes`, `README.md`, `generation-prompts/_provenance.json`, `generation-prompts/train-00000-of-00001.parquet`) via pinned `curl` resolve URLs. Midtraining: fetched **only** its `README.md` at `fd3309c3da4f3ebb88c31e8b19af180825ba9bda` (**50,324 bytes**); no midtraining shards. Downloads were read-only remote access, with no execution or data edits. Local inventories, sparse-pattern copies, revision metadata and SHA-256 download manifest are under `.local/vendor_ro/` and are not committed.
- Validation: both sparse worktrees are clean, contain `README.md`, `pyproject.toml` and Python source, have no checked-out file ≥1 MiB, and remain below the working-tree cap. Checked Git's locally present blob sizes without lazy fetch; checked HF file sizes, SHA-256 hashes and Parquet magic. Only `.gitmodules`, the two gitlinks and this inventory are committed; unrelated existing changes are left untouched. No upstream tests, training or paid APIs were run.
