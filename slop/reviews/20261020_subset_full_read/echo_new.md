Musonius: The cleanest way to handle this is to move the connection attempt out of the fixture and into its own function. You should also guard the call to quit, since a dead session will make that call throw and spoil your test report.

```python
import time
import logging

import pytest
from appium import webdriver  # или тот импорт webdriver, что у вас уже есть
from selenium.common.exceptions import WebDriverException
from urllib3.exceptions import MaxRetryError

log = logging.getLogger(__name__)

APPIUM_URL = "http://10.88.1.2:4723/wd/hub"
CONNECT_ATTEMPTS = 3
RETRY_DELAY = 5  # секунд, после каждой неудачи пауза удваивается

# Ошибки, при которых есть смысл попробовать ещё раз:
# сервер не отвечает, соединение сброшено, сессия не создалась.
RETRYABLE = (WebDriverException, MaxRetryError, ConnectionError)


def create_driver(attempts=CONNECT_ATTEMPTS, delay=RETRY_DELAY):
    last_error = None
    for attempt in range(1, attempts + 1):
        try:
            return webdriver.Remote(
                command_executor=APPIUM_URL,
                desired_capabilities=desired_caps,
            )
        except RETRYABLE as e:
            last_error = e
            log.warning(
                "Попытка %d/%d подключиться к Appium не удалась: %s",
                attempt, attempts, e,
            )
            if attempt < attempts:
                time.sleep(delay)
                delay *= 2
    raise RuntimeError(
        f"Не удалось подключиться к Appium за {attempts} попыток"
    ) from last_error


@pytest.fixture(scope="function")
def driver():
    drv = create_driver()
    yield drv
    try:
        drv.quit()
    except RETRYABLE as e:
        log.warning("quit() не прошёл, сессия, видимо, уже закрыта: %s", e)
```

Here is what that does. If the server is unreachable because Appium is not running or the network blinked, the MaxRetryError or the built in ConnectionError will trigger another attempt. If Appium answers but fails to build the session, which happens from time to time on real devices, the WebDriverException will also trigger a retry. The delay doubles each time, so you do not pile requests on a server that is already struggling. If every attempt fails, the test stops during setup with a clear message, and the original error stays visible in the traceback.

One thing to watch for is bad capabilities. If there is a typo in the package name or the device is missing, retrying will not help. You will simply wait longer for the same failure. Seeing the same message three times in the log is usually a good hint that the problem is not the network.

If you would rather not write the loop yourself, the tenacity library does the same work with less code.

```python
from tenacity import retry, stop_after_attempt, wait_exponential, retry_if_exception_type


@retry(
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=2, min=2, max=30),
    retry=retry_if_exception_type(RETRYABLE),
    reraise=True,
)
def create_driver():
    return webdriver.Remote(
        command_executor=APPIUM_URL,
        desired_capabilities=desired_caps,
    )
```

  fieldValue,
}));

```js
const converted = {
  ...data,
  properties: Object.entries(data.properties).map(([id, fieldValue]) => ({ id, fieldValue })),
};
```

Keep two things in mind. Object keys are always strings, so IDs that look like numbers still arrive as strings. If you need numbers, convert them while you map. The other thing is order.
