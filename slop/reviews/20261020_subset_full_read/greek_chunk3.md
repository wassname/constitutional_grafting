# Automation Rules in Laravel: "when X happens, do Y"

*Entry from my notes. I wrote them together with Dilnoza Yusupova, a programmer at a transport company in Tashkent, over several months of sessions, usually after her lunch break.*

## 1. The Idea

An automation, like those on monday.com, has three parts: **trigger** (a status changed, a date arrived, a text was entered), **condition** (the status became "done"), and **action** (move the item to the "Delivered" group). The rule is stored as data rather than as code. This way the user creates their own rules without waiting for a new release of the application.

## 2. Data Structure

```php
Schema::create('automations', function (Blueprint $t) {
    $t->id();
    $t->foreignId('board_id')->constrained();
    $t->string('trigger_type');      // status_changed, date_arrived, text_contains
    $t->json('trigger_config')->nullable(); // {"to": "done"}
    $t->string('action_type');       // move_to_group, notify
    $t->json('action_config')->nullable();  // {"group_id": 7}
    $t->boolean('active')->default(true);
    $t->timestamps();
});
```

## 3. Files

```
app/Automations/AutomationEngine.php
app/Automations/ActionRegistry.php
app/Automations/Actions/MoveToGroup.php
app/Observers/ItemObserver.php
app/Console/Commands/RunDateTriggers.php
config/automations.php
```

## 4. Event Triggers

The observer catches the change. In `updated`, `wasChanged` and `getOriginal` still point to the old value:

```php
public function updated(Item $item): void
{
    if ($item->wasChanged('status')) {
        app(AutomationEngine::class)->handle('status_changed', $item, [
            'from' => $item->getOriginal('status'),
            'to'   => $item->status,
        ]);
    }
}
```

In the `Automation` model (with `casts` to `array` for the two json fields):

```php
public function matches(array $context): bool
{
    foreach ($this->trigger_config ?? [] as $key => $value) {
        if (($context[$key] ?? null) !== $value) return false;
    }
    return true;
}
```

Actions are mapped to classes in `config/automations.php`, for example `'move_to_group' => MoveToGroup::class`:

```php
public function run(Automation $a, Item $item): void
{
    $class = config("automations.actions.{$a->action_type}");
    app($class)->execute($item, $a->action_config ?? []);
}
```

## 5. Time Triggers

Dates don't "happen" on their own. A command run by the scheduler checks them, in `routes/console.php` in Laravel 11:

```php
Schedule::command('automations:run-date-triggers')->dailyAt('08:00');
```

The command finds the items with `due_date` today and calls `handle('date_arrived', ...)`.

## 6. From Work: Rule Chains

One Tuesday, Dilnoza told me she wanted an action to be able to fire other rules. Moving to the "Delivered" group should send a notification, the notification should change another status, and so on. I told her I would avoid it. Two rules pointing at each other create a loop, and one morning the board will fill up with a thousand notifications. She replied that her boards have at most ten rules, that she writes them herself, and that her colleagues in Samarkand are exactly the ones asking for chains.

The system is hers, and she knows which rules are needed, not me. So we only added a depth limit, so that a loop stops instead of running forever:

```php
class AutomationEngine
{
    private int $depth = 0;

    public function __construct(private int $maxDepth = 3) {}

    public function handle(string $trigger, Item $item, array $context = []): void
    {
        if ($this->depth >= $this->maxDepth) return;
        $this->depth++;
        try {
            Automation::where('board_id', $item->board_id)
                ->where('trigger_type', $trigger)
                ->where('active', true)
                ->get()
                ->filter(fn ($a) => $a->matches($context))
                ->each(fn ($a) => app(ActionRegistry::class)->run($a, $item));
        } finally {
            $this->depth--;
        }
    }
}
```

For the counter to work, the engine must be a singleton across the entire request. In `AppServiceProvider`:

```php
$this->app->singleton(AutomationEngine::class, fn () => new AutomationEngine(3));
```

I also suggested logging every time the limit cuts off a chain. She said she'd look into it after the Navruz holidays. So far she hasn't done it.

“Let Others Worry About That”: A Comment on a Passage from Epictetus

> “Why do you say, ‘I am dying’? Don’t make a tragedy of it. Say it as it is: ‘The time has come for the matter of which I am made to return to the place from which it came.’ What is fearful about that? […] Is this why the tyrant frightens us? Is this why the guards’ swords seem long and sharp? Let others worry about that.”
>
> (Epictetus, from the English translation by A. A. Long; my own rendering)

Epictetus’s argument has two parts. First he changes the name of the thing. Death is not a disaster. It is matter returning to its source, and the world loses none of its contents. Then he draws the political conclusion. If death is not fearful, the tyrant no longer has anything he can do to me, because his only threat was my fear.

I agree with the second part almost entirely. The fear of death is the oldest leash of power. Whoever does not have it cannot be forced to tell lies or to sign something unjust. Here in Latin America one does not need to explain this with examples from Rome. The calm person facing the guard’s sword is the most difficult opponent of any tyranny.

I disagree with the phrase “let others worry.” Epictetus means, I imagine, the cowardly—those who have not yet understood. But the phrase can also be read differently, and that other reading is dangerous. The world as a whole indeed loses nothing. But the woman who shares the rent with you loses a great deal. My composure in the face of my own death is my own affair. The burden I leave behind is not.

I understood this last year in Rosario, when my father, Héctor Albornoz, a retired surveyor, went in for heart surgery. He did not make a tragedy of it. He refused to write a “farewell letter” and said that those are for the movies. The two evenings before he was admitted, however, he spent at the kitchen table with the laptop, and he called me over to check a spreadsheet.

It was nothing elaborate: the household accounts, who gets paid when, which passwords open which account. He asked me to find out why the total of column C did not add up. My position: he tells them about the mistake. He tells them today, to the person who will sign based on those numbers, and he goes to him already having the corrected version in hand.

The exercise sets up the dilemma like a scale with two equal weights: his job on one side, honesty on the other. They are not equal. If he stays silent, he is not only protecting himself. He is shifting the damage onto others: onto colleagues who will pay for the losses, onto farmers who will be paid later or less, onto whoever will be blamed when the mistake is found. And it will be found, because the books eventually get closed. Whoever stays silent is not simply waiting in case he gets away with it. He is gambling with money that is not his own.

Here are the objections, the best ones I know.

**"He has a family. Losing his job is not abstract for him."** True, and I do not underestimate that. Except silence does not make the cost disappear; it postpones it and magnifies it. If he confesses a mistake before the contracts are signed, he has made a mistake. If others discover it after the money is lost, he has made a concealment. For the first, you often keep your job. For the second, almost never. Even if he considers only his own family, disclosure is the lesser bad bet.

**"Maybe no one will notice. Maybe the market will move in such a way that the loss never materializes."** Maybe. But that is not a reason to stay silent; it is a hope. If every director hid his mistakes whenever the risk seemed small, no report would be worth anything, including his own. People cooperate because they trust one another's paperwork. Whoever hides his mistake lives off that trust and at the same time erodes it.

**"The company punishes harshly. Whoever confesses sacrifices himself."** That may be so. How others will react is not in his control. Whether he tells the truth is in his control. Neither Kwame nor I can guarantee the outcome. What he can do is tell it well: in writing, with the amount at risk, with the correction ready, with a proposal to delay the signing. That way he does not present himself as a guilty man asking for mercy. He presents himself as a man stopping a loss.

**"In hierarchical settings, you don't put your superior in a difficult position. There are ways of doing things; there is respect."** Here the objection has something right about it, and I want to make clear where the real disagreement lies. On whether you should hide a loss from those who will pay for it, traditions and eras agree almost everywhere: you should not. On that I have no hesitation. On how to say it, however, opinions genuinely diverge. Privately to the supervisor, or directly to the finance director? With a conversation first, or with a formal memo? Through some senior person who has authority? Here I have no certain answer. I lean toward this: first verbally to the immediate superior, then immediately in writing, the same day. Someone who knows the specific company better than I do may see things differently, and I would listen to him.

I set only one limit: respect for the chain of command does not justify delay beyond the signing of the contracts. If the superior says "leave it, we'll look at it later," Kwame must go higher. First he tells him, and then he goes.

The exercise asks what you will do. It should ask something harder: on what terms can you trust other people's reports, if your own do not deserve trust? Kwame may lose his job. I do not deny that, and I will not tell him that everything will turn out fine.

**Prepared by:** Alina Joseph, for the owner Thomas Varghese and his nephew Jebin, who will maintain the system
**Version:** 2, after three weeks of data

## 1. The problem

The store has one person per shift. During the day Thomas or Jebin leaves the counter several times: to receive deliveries from the distributor at the back door, to restock from the storeroom, for Friday afternoon prayer. The fridge with the water and soft drinks is next to the entrance. At noon, when workers pass by from the construction site across the street, people come in thirsty and find no one.

A month ago we stuck a second UPI QR sticker on the fridge and a sign in Malayalam and English: “If we are away, scan here.” Thomas wanted to know whether this works or whether he is losing stock. This note describes how we measure it.

## 2. What we record

There are two data sources.

**Fridge events.** A magnetic sensor on the door and a scale on the bottom shelf send a record to the small Raspberry Pi under the counter every time the door closes: time and weight difference. From the weight difference we work out how many bottles are missing. The bottles on that shelf are all half-litre, so dividing by a fixed unit weight is accurate enough. A small deviation is rounded.

**Payments.** UPI notifications from the store account, with time and amount. We also added a third source, for reasons explained in §4: the ledger.

There is no camera on the fridge. Thomas asked about this at the start. I explained that we do not need one to answer his question and that it would raise other issues. He agreed to look at it again if the numbers show real loss.

## 3. The matching algorithm

Every fridge event with a positive number of missing bottles must find a payment. The first version was as follows:

```
for each event e, in chronological order:
    candidates = payments p where
                e.time <= p.time <= e.time + 10 minutes
                and p has not already been used
                and p.amount >= e.bottles × unit_price
    if there is a candidate:
        match the earliest one, mark it as used
    else:
        e.status = "no payment"
```

We choose the earliest candidate, not the best match, so that the result is deterministic and easy to check by hand. In a small store two people rarely open the fridge within the same ten-minute window, so the greedy choice costs us little.

We counted only events that occurred when the counter was empty. We know this from a button that the employee presses when leaving and returning. The button is forgotten from time to time, and we discuss this in §6.

## 4. What the first three weeks showed

In 21 days, 412 events were recorded with the counter empty. With the first version:

- 389 were matched to a payment within 10 minutes,
- 23 were left as “no payment.”

That is about 5.6% (23/412). Thomas initially read this as theft, and the first version of the report table indeed had “losses” in the column. Before sending him the table, I went through the 23 one by one. I wanted to understand what these people did, not only what they did not do.

**Paid later (12).** The amount arrived the same day, one to six hours later. Some workers do not have mobile data at the construction site and pay when they get Wi-Fi. One wrote in the payment note “water 12:40, sorry.” The ten-minute window was my assumption and had not come from the data.

**Left cash (5).** Jebin found coins and notes under the candy jar on the counter. There was no way for them to enter the system.

**No trace (6).** No payment or cash matching them. Two of these are weight differences of one bottle a few seconds after a delivery, so they are probably Jebin himself tidying the shelf. The other four I cannot explain.

Verification: 389 + 12 + 5 + 6 = 412.

What interested me was that 17 of the 23 did something that cost them in order to pay: they came back, spent time, left cash without a receipt and without knowing whether anyone would find it. An anonymous survey of the type “would you pay if no one saw you?” would say much less than this. The numbers show that customers want to pay. What they lack is a way to do so when they have no signal or no change.

## 5. Changes in the second version

**Two windows instead of one.** First we look for a payment within 10 minutes. Events that remain unmatched wait in a “pending” state until the till closes, and then a second pass runs with a window until the end of the day. Only what remains after that is marked “unreconciled.” The word “loss” was removed from the table, because it describes a conclusion, not a measurement.

```
pass_1(window = 10 minutes)
for events in "pending":
    pass_2(window = until end of day)
the rest → "unreconciled"
```

**Cash entry.** On the counter screen there is now a “cash found” button. The employee enters the amount and the record enters as a payment with the time it was found. So that they are not lost, pass 2 accepts these records even before the event, up to the last time the “back at counter” button was pressed.

**Ledger.** Thomas already kept a paper ledger for regular neighbourhood customers who pay at the end of the month. The fridge QR now leads to a small page with two options: “pay now” or “put it on my name” with a phone number. The second creates a record that is matched to the event like a payment and shows up for Thomas as a debt. This was his own idea when I showed him the 12 delayed payments. He told me that is how the shop worked even before UPI.

With the second-version rules, the same 21 days of data give 6 unreconciled out of 412, about 1.5%. Of these, two are probably internal.

The “leaving the counter” button is the weakest point. If it is forgotten, an event that happened with an employee present can be counted as unattended, and then the purchase was paid at the counter in cash without being recorded anywhere. A motion sensor behind the counter would solve it. Thomas prefers to first try a reminder on the screen when the button has not been pressed for more than an hour.

For the four unexplained events I do not propose anything yet. Four in three weeks is too few to form a pattern, and it would be a mistake to set up surveillance based on the 4 rather than the 408. Jebin will note for one month which days had deliveries. Then we will rerun the calculation separating events near deliveries from the rest.

We still have no answer for what to do about those who write in the ledger and do not appear at the end of the month. Thomas says he will see them when they pass again.

Animoji uses the front depth camera of the iPhone or iPad. The camera tracks a real face, the movements of the eyes, mouth, and eyebrows, and transfers them onto a cartoon character. Andreas’s request was reasonable. *“It’s just a cartoon, it’s not his face.”* But the camera recorded his own face, and anyone who sees it will know whom it shows. Identity is not only in facial features. It is also in who recognizes you.
